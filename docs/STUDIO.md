# Astreon Studio: the browser game studio

**Goal:** one studio, in the browser, that a first-time maker and a professional use side by side. The first game takes a few minutes. The tenth is a networked game with its own tools. The same page, the same project and the same code carry them the whole way, with nothing to install and no account. For professionals it aims to be the best place to make a game that is meant to run in a browser.

This page is the design. The riskiest parts have been tested in a feasibility spike (see **Spike results** below); the studio itself is not built yet.

## Decisions made

| Question | Decision | Why |
|---|---|---|
| Where does it run? | A **web app**: the browser only, no install; no server needed to make a game | Works on any computer, a school Chromebook or a studio workstation; the same code can later sit in an Android shell |
| Dependencies | **Zero**, same as the engine: our own code editor, docking, panels and visual tools | Keeps the project auditable and the studio small and fast to load |
| Who is it for? | **Ages 15 to 60, from first-timers to professional developers** | The studio is not made simpler for beginners; it is made *learnable* (see pathways) |
| Beginners | A **guided pathway inside the real studio**, not a separate easy mode | What they learn is the tool they keep using; nothing is thrown away when they grow |
| 2D or 3D first? | **2D first**; the existing 3D scene editor becomes a panel later | Most first games are 2D; the 3D editor already exists |
| Where is code written? | **In the studio**, next to the live game | Nobody should leave the page to make a game |

## What research says (and what we do with it)

The evidence on game-engine editors specifically is thin. A review of VR engines reports that beginners struggle with complex interfaces and rely on scattered tutorials ([arXiv 2508.13116](https://arxiv.org/pdf/2508.13116)), and an interview study of 27 game-startup developers found that learning curves and tools that do not adapt to their needs slow them down ([arXiv 1908.04629](https://arxiv.org/pdf/1908.04629)). Neither measured the editors of Unity, Unreal or Godot, so we lean on adjacent evidence and on testing with real people (below).

| Finding | Source | What it means for the studio |
|---|---|---|
| Showing something on the first screen signals that it matters; hiding advanced features helps novices and costs experts nothing, if essentials are not buried | [Nielsen on progressive disclosure](https://brajeshwar.com/2006/progressive-disclosure-by-jakob-nielsen-usability-expert/) | **Workspaces**: each shows what its job needs and nothing else; everything is one search away |
| Hands-on practice teaches mechanics better than reading; a research prototype for Unreal found that clear instructions, room to explore and guidance embedded in the tool helped comprehension without hurting engagement (small samples) | [Wayline](https://www.wayline.io/blog/designing-effective-game-tutorials-and-onboarding), [HAW Hamburg thesis](https://reposit.haw-hamburg.de/handle/20.500.12738/19699?locale=de) | **Pathways** run *inside* the real studio, on the student's own project, and check what they actually did |
| A command palette lets people find features that would never earn a button; Blender's own F3 search only matches command names and misses objects and settings | [Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/) | **One search for everything**: commands, files, entities, settings, API docs and lessons; ranked and showing each shortcut |
| Result order matters: VS Code kept alphabetical order so results do not reshuffle with every keystroke | [VS Code issue](https://lightrun.com/answers/microsoft-vscode-add-fuzzy-search-to-commands-in-palette) | Recent and exact matches first, then a stable order; tested with people |
| Immediate feedback and a game that is always running make creators more productive and creative; a live game environment can use snapshots to replay the situation around a code change | [QMUL 2019](https://gameai.eecs.qmul.ac.uk/2019/06/15/martin2019towards/), [VL/HCC 2021](https://conf.researchr.org/details/vlhcc-2021/vlhcc-2021-vl-hcc-main-conference/29/Shortening-Feedback-Loops-in-a-Live-Game-Development-Environment) | The game **never stops while you edit**; changes show at once, with the numbers you tune as sliders |
| No game editor was found that combines live coding, hot reload and time-travel debugging; the closest is an experimental debugger for the Bevy engine | search results (Revy) | **The Time Machine** (below) is our chance to be different, and our deterministic rules make it possible |
| Blocks help motivation more than later achievement, and moving from blocks to text is a known hurdle | [Armoni et al., 2015](https://cris.iucc.ac.il/en/publications/from-scratch-to-real-programming/) | Code is first-class from the start; visual logic is an *option*, not the entry path |

## Design principles

1. **Never stop the game.** Editing code, art, levels and numbers changes the running game within a blink, keeping its state where possible.
2. **Direct manipulation.** Drag a thing in the game view and its numbers in the code or data change; edit a number in the code and the thing moves. One source of truth, many views.
3. **Never lose work.** Autosave on every change, a history you can open and restore, undo everywhere, and export at any time.
4. **Say what to do, not what went wrong.** Every error names the line, explains it in plain words and offers a fix ("`hero.jump` is not a thing; did you mean `hero.jumpsWith`?").
5. **Everything is discoverable and everything is fast.** Menus for the curious, one search for the sure, shortcuts shown wherever they exist, and the whole studio usable by keyboard alone.
6. **Guidance, never gates.** Pathways suggest and explain; they never lock a feature. A professional can ignore them completely.
7. **The same project everywhere.** A studio project is an ordinary engine project (the `create-game` layout): it runs in `npm run dev`, passes `npm test`, builds with `engine-build`, and can live in git. Leaving the studio must be easy, and so must coming back.
8. **Open by design.** Panels, inspectors, importers and exporters are plugins using the same API the built-in ones use.

## One studio, three depths

The studio does not have a "kids mode". It has **workspaces** (a set of panels arranged for a job) and a **pathway** (a guide that can be on or off).

| Workspace | What is on screen | Used for |
|---|---|---|
| **Make** (the default) | The live game, a short list of what is in it, an inspector for the selected thing, and the pathway card | Moving things, tuning values, trying ideas |
| **Code** | The code editor beside the live game, with the console and API help | Writing the rules |
| **Art** | The sprite painter, animation timeline and level painter | Pixels, tiles, maps |
| **Sound** | The sound maker and the mixer | Effects and music |
| **Debug** | The Time Machine, entity inspector, profiler, network lab | Finding out why |
| **Ship** | Web health report, build size, export and publish | Getting it to players |

A professional rearranges panels, saves layouts and lives in Code and Debug. A beginner starts in Make with the pathway card. Both press the same one key (<kbd>Ctrl</kbd> + <kbd>K</kbd>) to find anything.

## Pathways: the learning route built into the studio

A pathway is a sequence of **hands-on missions** that run on a real project, with the studio watching what the student does:

> **Mission 4: make the hero jump.** Open the Editor panel. Find the line that says `speed`. Change the number and watch the hero. *The studio highlights the line, waits for the change, and shows the sliders; when the hero's speed has changed it says so and offers "Why does this work?" and "Next".*

Each mission has a goal, a nudge (shown after a quiet moment), a hint (on request), the full answer (last), a check that looks at the project and the running game, and a "go deeper" link to the guide. Progress is saved in the project, so it works offline.

The pathway is a route from first game to professional work, in stages. Every stage ends with a game the student keeps:

| Stage | They make | They learn |
|---|---|---|
| 1. Make something move | A character that runs and jumps | Sprites, input, the game loop, changing a number |
| 2. A real level | A level with coins, spikes and a goal | Levels, collision, events, scoring |
| 3. Enemies and feel | Enemies, sound, camera, particles | Behaviour, juice, the feel of a game |
| 4. A whole game | Menus, levels in order, saved progress | Scenes, UI, saving |
| 5. Make it yours | Their own art, sounds and rules | The painters, reading and changing engine code |
| 6. Go online | A turn-based or real-time multiplayer game | Servers, prediction, accounts, matchmaking |
| 7. Ship it | A published game with a web-health report | Performance budgets, the build, sharing |
| 8. Go deeper | 3D scenes, plugins, a custom panel | The engine, its packages and how the studio itself is built |

The same missions can be used by a teacher as a course and by a company as onboarding for new staff.

## What makes it the best studio for browser games

Browser games have problems that desktop studios do not measure. The studio does:

- **Web health** (Ship workspace): download size, time until playable, memory, frame time on a throttled CPU, and what happens on WebGPU, WebGL2 and Canvas2D (one switch to try each). Budgets can fail a build.
- **Input on every device**: keyboard, gamepad and touch tested live, with on-screen controls designed in the studio.
- **Audio rules**: sound that only starts after a click is handled and shown as a warning where it matters.
- **Offline and installable**: a one-click PWA export; asset hashing, compression and atlas packing already exist in the build tool.
- **The network lab** (Debug): run a server and several clients from one button, with latency and packet loss sliders, the packet inspector, and prediction error graphs. This is already built into the engine (`debug`, `transport`'s simulator, the load tester) and only needs a home.
- **Cross-browser determinism check**: the same replay hashed on Chrome and Firefox, the way `tools/determinism.js` does for the engine.

### The Time Machine

Our rules are deterministic: the same inputs give the same game. So the studio can record every input and every few seconds a snapshot, and offer:

- **Scrub back** through what just happened with a timeline, and play it forward again.
- **Change the code while paused in the past**, then re-run from that moment: "what if the jump were higher?" without replaying by hand.
- **Branch**: keep two versions of a moment side by side.
- **Share a bug** as a file: a replay that reproduces it exactly on someone else's machine, or in CI.

No other game editor found in our research combines live coding with this. It is the feature to build the studio's identity on.

## The studio, piece by piece

| Piece | What it is |
|---|---|
| **Project store** | Projects live in the browser (IndexedDB) and can be linked to a real folder on disk (the File System Access API) for git and other tools; zip export and import |
| **Run** | The game runs in a sandboxed frame; the page watches a heartbeat and replaces the frame when the code hangs |
| **Code editor** | Our own, no dependencies: highlighting, line numbers, bracket matching, auto-indent, multi-cursor, find and replace, error underlines, autocomplete and hover help generated from the same JSDoc as the API reference, number sliders on <kbd>Alt</kbd> + drag |
| **Inspector** | Edit anything in the running game: entities, components, resources; changes can be kept or thrown away |
| **Sprite and level painters** | A pixel editor with layers, frames and palettes; a tile and entity painter that reads and writes the same text level format the games use |
| **Sound maker** | Controls for the synthesiser specs, with a play button and a library |
| **Scene editor (3D)** | The existing editor, as a panel |
| **Visual logic (later)** | "When the hero touches a coin: add 1 to the score" as rules, generating code; an option for people who prefer it, with every rule showing its code |
| **Plugins** | Panels, importers, exporters and inspectors written against the public studio API |
| **Search and help** | <kbd>Ctrl</kbd> + <kbd>K</kbd> finds everything; <kbd>F1</kbd> on any word opens its documentation with a "try it" example |
| **Localisation and access** | Text in a translation table from day one; keyboard-only use, screen-reader labels, high contrast, reduced motion |

### How a project runs in the browser without Node

The engine is plain ES modules, so no build step is needed. As proven by the spike:

1. The game runs in an **iframe on another origin** from the studio, so a project (yours, or one somebody shared) can never read the studio's own data.
2. Inside it, the game's code runs in a **Web Worker** and draws to an **OffscreenCanvas**. A worker can be killed, so a game stuck in an endless loop is stopped for good instead of burning a processor core until the tab closes.
3. A **service worker** on the runner's origin serves the project's files from a cache, so imports and file names are real. Workers ignore import maps, so `@engine/x` is rewritten to the engine file's own URL when the files are stored (on the same line, so line numbers stay true).
4. **Hot reload** imports the new version into the same worker; the game's **state is plain data** and stays. The worker also copies its state out about twice a second, which is the base of the Time Machine and of recovering after a hang.
5. **Mistakes show their place.** A syntax check loads a copy of the project as a module script that throws as its first act; the browser reports the exact file, line and column of any syntax error (a dynamic `import()` or a worker does not). Runtime errors are read from the stack trace.

The consequence for the game kit and for projects: **game code must not touch the DOM** (it runs in a worker). Drawing, sound and input go through the runner (sound plays on the main thread when the game asks for it). That is also what keeps rules separate from the picture.

## The game kit

The engine is powerful and low-level. A first game should not need an atlas and a sprite batch. A **game kit** (working name `@engine/arcade`) sits on top as an optional, batteries-included layer for the first hour and for quick prototypes:

```js
const hero = sprite('hero', { x: 40, y: 100 });
hero.walksWith('arrows');
hero.jumpsWith('space');
onTouch(hero, 'coin', (coin) => { coin.destroy(); score.add(1); play('coin'); });
```

It is not a toy: every name maps to engine packages (`core`, `physics`, `render`, `audio`, `input`, `save`), a project can use the kit and the engine in the same file, and the pathway shows what a kit call does underneath when the student asks.

## Safety and privacy

Some users are teenagers, so the first version collects **nothing**: no accounts, no analytics, no uploads. Projects stay on the device. Sharing is by file or link that holds the project itself. Anything online (a gallery, classroom features, collaboration) is a later decision with its own review (privacy law for minors, moderation, consent).

## How we will know it works

Targets, each tested with real people, not guessed:

| Measure | Target |
|---|---|
| New person to a running, edited game | under 5 minutes |
| A non-programmer finishing stage 2 of the pathway alone | under 60 minutes |
| An experienced developer opening an existing engine project and being productive | under 10 minutes |
| Lost work after a crash, a closed tab or a power cut | none |
| Everything reachable by keyboard | yes, checked by test |
| Studio start-up on a mid-range laptop | under 3 seconds to a usable editor |

**Cold-start tests** with three kinds of people, as we did for the docs: a teenager new to programming, an adult hobbyist, and a working game developer. They run after the first usable version and after each workspace is added. What they struggle with becomes the next fix.

## Spike results (S0, measured)

The spike (`studio/spike/`, run with `node tools/studio-spike-test.js` and `node tools/studio-spike-compat.js`) tested the riskiest ideas in Chrome 154 and Firefox 157.

| Question | Result |
|---|---|
| Time from opening the studio to a running game | about 250 to 350 ms, with the service worker installing on first use |
| An edit reaching the running game | **6 to 20 ms**, keeping the game's place (time and score not reset) |
| Editing an imported file | reloads it too; the new helper is in use at once |
| Syntax error location | **exact file, line and column**, also for another file than the one run (needed the module-script check; plain `import()` gives none) |
| Runtime error location | exact file and line from the stack trace, in both browsers (their formats differ; the same code reads both) |
| A game stuck in `while (true) {}` | the studio froze for **1 to 14 ms** at most; the runner killed the worker and started a new one from the last copy of the state, and did not re-run the version that hung |
| A hung game recovering | the game carried on from its saved state (not from scratch) |
| Project survives reloading the page | yes (IndexedDB) |
| Zero-dependency code editor, 1,000 lines | our work about 1.6 ms per keystroke; keystroke to screen about 7 ms |
| Zero-dependency code editor, 10,000 lines | our work about 1.5 ms, but the browser re-lays the whole textarea out (about 8 ms): keystroke to screen about 16 to 22 ms (p50 / p95); scrolling about 8 ms |

What the spike also taught:

- **An iframe alone is not enough.** First attempt: the game ran on the page of the frame, which protected the studio but could not be recovered, because a replacement frame on the same site shares the stuck process. The Worker fixes that, and the frame stays for security.
- **The textarea-over-highlighting editor is fast to about 5,000 lines** and fine at 10,000. The cost that grows is the browser's own text layout, not our code. A custom-rendered editor (a hidden input for typing, our own drawing of the visible lines, caret and selection) would make the cost independent of file size; it is a rewrite of the editor's core, and is only needed if real projects reach very large files. Decide at S2 with the real editor features in place.
- **Safari is untested** (no Mac here): its support for service workers inside cross-origin frames, rendering in workers and module workers needs a check before a release. Chrome and Firefox pass identically.
- **The state must be plain data** (it is copied with `structuredClone`). The studio can say so in plain words when a game stores something else; it already does in the spike.

## S1 results (the studio shell, built and tested)

`studio/` is now a working application (run it with `npm run studio`; details in `studio/README.md`). It has projects and files, a code editor, the live game, console, history, the search box, menus, settings, and rearrangeable panels with two workspaces (Make and Code). About 4,000 lines of code with no dependencies.

- **Tests:** 37 unit tests in `npm test` (search ranking, shortcuts, commands, settings, the dock layout model, the store, zip handling including a zip bomb, message checking, the highlighter), and a Chrome test with real mouse and keyboard events that makes 72 checks (`node tools/studio-test.js`).
- **It is fast:** typing to the running game takes about 10 ms; a new project to a running game about 230 ms.
- **Work is never lost:** every change is saved at once; a failed save is announced and the work stays in the tab; restore points keep identical contents once; going back first keeps what you had; deleted files and projects can be undone; a zip bomb is stopped while it expands.
- **Everything is a command:** menus, search, shortcuts and settings share one list, so every action can be found and has its shortcut shown; shortcuts can be changed (F1) and clashes are reported.
- **Accessibility basics tested:** every control has a name, no duplicate ids, tab lists and panels have roles, live regions announce messages, everything works from the keyboard.

What building it taught, which changed the design:

- **A frame that moves reloads.** Dragging a panel or switching a tab rebuilt the page around the game's frame, which restarted the game and lost its state. The frame now lives outside the panel layout and is laid over the Game panel's empty slot, and switching tabs updates only what is shown.
- **Name collisions are real bugs.** The dock's `row` class collided with the list-row style and squashed whole panels; direction classes are now `dir-row` and `dir-column`. A test that drags a splitter caught it.
- **The browser's DevTools typing shortcut moves the caret to the end of a text box** (real typing does not), so the end-to-end test types through the browser's editing command, as a keyboard does.
- **Everything from the game's frame is untrusted** (it may be somebody else's code): each message is checked, shortened and copied before the studio uses it.
- **Not yet tested:** the studio in Firefox and Safari (only the S0 runner was), touch screens, and a screen reader in use (only the structure was checked).

## S2 results (the code editor, built and tested)

- **Helpers while you type** (`studio/app/editing/ops.js`): Enter keeps the indentation and opens a block between brackets; typing ( [ { or a quote closes it, typing the closer steps over it, Backspace removes an empty pair, a selection is wrapped; Tab and Shift+Tab indent; <kbd>Ctrl</kbd>+<kbd>/</kbd> comments; <kbd>Alt</kbd>+arrows move a line; matching brackets are marked. Every change goes through the browser's own editing command, so undo and redo work as everywhere else.
- **Suggestions from our own API docs**: `tools/studio-api-index.js` builds a 170 KB index of 507 exports (and the members of each class) from the same JSDoc as the API reference, and `npm test` fails if it is out of date. The list ranks your own names first, then imported names, then the whole engine; choosing an engine name that is not imported yet adds its import line in the same undo step. After a dot it offers the members of what the variable was made from (`const w = new World()` then `w.`). Hovering a name, or being inside a call, shows its signature, description and the current parameter.
- **Find and replace** (<kbd>Ctrl</kbd>+<kbd>F</kbd>, <kbd>Ctrl</kbd>+<kbd>H</kbd>, <kbd>F3</kbd>): match case, whole word, patterns; an invalid pattern gives a message, matches are capped at 5,000, replace-all is one undo step.
- **Friendly errors** (`friendly.js`): the browser's message is kept and a plain-words meaning and a thing to try are added, with "did you mean" for a misspelt name (edit distance over your names and the API). The error is underlined in the code, the line number goes red, hovering shows it, and the underline goes when the next run succeeds.
- **Everything is a command**: Find, Replace, Comment, Move/Copy/Delete line, Show suggestions (<kbd>Ctrl</kbd>+<kbd>Space</kbd>), Show help (<kbd>Ctrl</kbd>+<kbd>I</kbd>) are in the Edit menu, the search box and the shortcut settings.
- **Tests**: 22 new unit tests (`studio/test/editing*.test.js`) and 17 new Chrome checks with real key presses. 801 unit tests pass.
- **Limits, honestly**: suggestions are by name and by what a variable was made from, not by real type analysis, so a value returned by a function has no member list. A pattern search can be slow on a pathological expression (the match cap does not stop the regular expression engine). Brackets typed with an IME or on keyboards where a bracket needs AltGr are handled but untested on real hardware. <kbd>Ctrl</kbd>+<kbd>Space</kbd> is also the input-method switch on some Windows setups; suggestions appear by themselves while typing, and the shortcut can be changed.

## S3 results (the game kit and pathway stages 1 and 2)

- **`@engine/arcade`** (`packages/arcade`, 9 unit tests): the game kit. Things are plain objects in a list in the game's state (so hot reload, saving and rewinding need no care): `spawn`, `all`, `first`, `despawn`, `touches`; keys by easy names (`held(keys, 'left')`, WASD works too); `walk`, `steer`, `jump`, `gravity`, `moveAndCollide` (stops at walls, cannot tunnel through thin ones); `loadMap` (levels as rows of letters, with clear messages for a ragged row or an unknown letter); `clear`, `drawThings` (boxes, circles, emoji), `label`, `follow` (camera); seeded `random` kept in the state so a game replays the same way. It does not touch the page, so it runs in the game worker. **Honest note**: unlike what the earlier plan said, it does not wrap the other engine packages; it is a small separate layer, and the README says where to go when a game outgrows it.
- **A template**, *Run and jump*: a hero that runs, jumps and collects coins, with `SPEED` and `JUMP` at the top to change while the game runs. Chrome test: it lands, runs, jumps, and changing `SPEED` changes the running hero.
- **The pathway engine** (`studio/app/learn`, pure logic, 10 tests): a pathway is stages of missions; a mission has a task, a *check* (a function that reads the project's files, the numbers the running game reports, or things the studio saw happen), up to three hints, the full answer last, an optional "make this change for me", a line to highlight, and a "why does this work". A check only counts when the game is running without an error. A number that is changed to something silly gets a kind note, not a pass. A broken check can never trap a student, and the guide can be skipped, turned off or restarted at any time.
- **Stages 1 and 2, 11 missions**: play, change `SPEED`, change `JUMP`, add a coin to a level made of letters, paint the hero, save a restore point; then load a bigger level from another file (the studio adds `src/levels.js`), make the camera follow, add spikes, collect every coin (played, not coded), say "You win!". A unit test follows the reference solution through all 11 missions and checks that each mission is not done at its start and is done after the solution; every level coin is reachable (random-play check).
- **The Learn panel and workspace**: a card beside the code with the task, progress dots, hints on request, a nudge after 45 quiet seconds, the answer last, and the highlighted line in the editor. The start page has a "Start the guided route" banner; the same studio is behind it, nothing is hidden or locked. Progress is saved per project (IndexedDB) and not in the zip export.
- **Something the Chrome test taught**: a game keeps its state when code is hot-reloaded, so a change made in `create` (the level, the map) only shows after **Run** starts the game over. Missions now say so, and `follow` throws "follow needs the size of the level... then press Run to start the game again" instead of a puzzling error.
- **Tests**: 120 Chrome checks (31 new) drive a whole student path with real clicks and typing: start the guided route, hints, a too-small number, every mission through to the finished card, skip, and turning the guide off. 820 unit tests pass.
- **Not done**: the cold-start test with real people (a teenager new to programming, an adult hobbyist, a working developer) that the targets need. The 11 missions are written for beginners but have not been tried by one. Sound is not in the kit yet (it needs the runner to play it on the main thread); it comes with the sound maker. The docs site links from missions are off until a docs address is configured.

## S4 results (the Time Machine and the Inspector)

- **The core** (`studio/runner/timeline.js`, pure, 12 tests): a recording is the *inputs* (a key down or up, a value edited by hand, each stamped with its tick) plus a copy of the state once a second. `seek` restores the copy before the target, starting one earlier so that the run crosses a copy and any difference from what was recorded shows, then runs forward applying the recorded inputs. A tick is one call of `update`, 1/60 s. The same file runs in the game's worker, in Node tests and in the command-line checker.
- **What it does**, in the worker and in the studio: **pause**, **step** one or ten ticks either way, **drag back** through up to ten minutes (bounded by 600 copies and 48 MB; the oldest go first, with their inputs), **play on from here** (forgets what came after) or **replay with my code** (runs the recorded key presses again with the code as it is *now*: "what if the jump were higher?"). Edits made in the inspector are part of the recording, so a replay makes them again at the same moment; an edit made while paused in the past is placed there.
- **Honest about chance**: if re-running a moment gives a different state from the one recorded, the studio says so ("this game did not repeat itself exactly at 2.0 s; it probably uses Math.random() or the clock; keep chance in the game state, as the kit's `random(game)` does"). Changing the code is not reported as a divergence.
- **The Inspector** (`state-tree.js`): the game's state as a tree. Numbers, text and switches are fields you can edit (only plain values over plain values, in places that already exist, never a path that could reach a prototype); the tree is only rebuilt when its shape changes, so values update in place without taking a field away while you type; a filter finds fields by name or value; clicking a thing outlines it in the game (a dashed box, camera-aware). A state over 150 KB is not shown, with a message.
- **Recordings as files**: *Save recording* writes one JSON file with the game's code, the start state, every input and a checksum per second. *Open recording* checks the file strictly (sizes, kinds, paths, no `..` in file names), makes a new project from it, pauses the game at its start and has the worker run the whole recording again, comparing every checkpoint: "reproduced exactly" or "does not match from tick N". `node tools/replay-run.js file.replay.json` does the same in Node (exit code 0, 1 or 2), so a bug report can be a CI test. Tested on the real *Run and jump* game: a changed `SPEED` or `JUMP` is caught, and so is a game using `Math.random`.
- **A Debug workspace**, a Debug menu, and commands: <kbd>F8</kbd> pause or play, <kbd>Alt</kbd>+<kbd>←</kbd>/<kbd>→</kbd> step, replay, save, open. The panels only ask the game for data while they can be seen.
- **Tests**: 12 timeline tests, 5 command-line tests, and 34 new Chrome checks (pause, step, clicking the timeline, F8, typing a number into the inspector, the filter, opening a recording in a new project, a changed recording, a file that is not a recording). 837 unit tests pass; the Chrome test has 154 checks.
- **Limits**: a game is reproducible only if all its chance and time are in its state (the kit does this; `Math.random`, `Date.now` and `performance.now` break it, and the check says so). Checksums are exact on one browser; the same recording checked on Chrome and Firefox is not yet tried (floating-point functions such as `Math.sin` may differ between engines, and this is the "cross-browser determinism check" still on the list). History is lost when the game worker is replaced after a hang (the state is restored, the recording starts again). The inspector edits runtime state only, not the code's constants such as `SPEED`; the code editor is where those change. Not built: *branches* (two versions of a moment side by side) and multiplayer recordings.

## Open questions

1. **How fast can our own code editor get?** Typing latency and large files are the risk of a zero-dependency editor. The spike measures it; if it fails, a textarea-based editor with fewer features is the fallback, not a dependency.
2. **Which platforms for the first release?** Desktop browsers (Chrome, Edge, Firefox, Safari) are the target; tablets and phones are viewing and light editing only at first.
3. **Visual logic: events or stacks?** Event rules suit games and our event model; stacks are more familiar. Decide with a prototype and real users.
4. **Python or other languages?** Not now. JavaScript with JSDoc types is the language of the engine and the browser.
5. **Hosting and sharing.** Where the studio lives (a static host, a school server, a folder) decides what "Share" can mean.
6. **Collaboration** (two people in one project). Valuable for teams and classrooms, and needs a server and a conflict model; later, after S6.
