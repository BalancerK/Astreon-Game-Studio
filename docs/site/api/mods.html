@engine/mods

Safe third-party mods: manifests, content-hashed bundles, sandboxed script mods in confined processes, signing, policy, validated commands (guide: docs/MODDING.md, threat model: docs/SECURITY.md).

npm install @engine/mods

Version 0.1.0. The package's own README (packages/mods) explains how the pieces fit together; this page lists every export.

class ModManager#

class ModManager

Loads mods, runs script mods in confined sandboxes, and turns what they return into validated commands.

The game integrates in four steps: add bundles, start(), emitFrame(frame) on a timer (non-blocking), and drainCommands() each tick to apply what mods asked for. Slow or misbehaving mods are skipped, struck, and eventually disabled; none of this can block the caller.

class ModSandbox#

class ModSandbox

One mod, in its own confined process. Started with: --permission (no filesystem except reading the engine's own sandbox files, no child processes, no workers), --max-old-space-size (a runaway allocation kills the child, not the server), --disallow-code-generation-from-strings (even the child's own realm cannot eval), a scrubbed environment, no stdio, and below-normal OS priority. It does NOT block the network (Node 24's permission model does not cover it): see SECURITY.md.

Types#

Bundle#

A bundle is a manifest plus its files as text, plus an optional signature. The hash covers the manifest and all files, so it identifies exactly what will run. The client view is the data clients need (rules and client); it has its own hash, which the server advertises and clients verify before playing.

Type: Object

NameTypeDescription
manifestimport('./manifest.js').ModManifest
filesRecord<string, string>path -> text (the entry script, extra data files)
signature (optional){key: string, sig: string} | nullEd25519: raw public key (hex) and signature over the bundle hash (hex).

CommandSpecs#

op name -> field name -> spec

Type: Record<string, Record<string, FieldSpec>>

FieldSpec#

Mods act on the game only through commands: small JSON objects the game defines and validates. The mod proposes, the game decides (and can refuse). A command spec lists exactly the allowed fields and their types.

Type: {type: 'int' \| 'number', min?: number, max?: number} \| {type: 'string', maxLength?: number} \| {type: 'bool'}

ModManifest#

A mod's mod.json. Strict on purpose: unknown fields are errors, so typos do not silently do nothing and a manifest cannot smuggle in fields a future version might interpret.

Type: Object

NameTypeDescription
idstringLowercase id; namespaces everything the mod adds.
versionstringx.y.z
engine (optional)stringEngine version range, e.g. ^0.0.1.
name (optional)string
description (optional)string
author (optional)string
tier'data' | 'script'
entry (optional)stringScript file (tier script only).
dependencies (optional)Record<string, string>Other mod ids -> version ranges.
rules (optional)Record<string, any>Tier 1: rule values (the game whitelists and range-checks them).
client (optional)Record<string, any>Presentation data sent to clients (the game whitelists it).
limits (optional){tickBudgetMs?: number, memoryMb?: number, tickEvery?: number}What the mod asks for; the server policy clamps it.
