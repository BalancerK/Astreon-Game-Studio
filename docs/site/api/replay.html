@engine/replay

Replays and spectating: record a match as compact snapshot deltas (seek anywhere, any speed) or as its inputs (a few KB, with drift detection), a delayed feed shared by any number of spectators.

npm install @engine/replay

Version 0.1.0. The package's own README (packages/replay) explains how the pieces fit together; this page lists every export.

class InputPlayer#

class InputPlayer

Plays an input recording back through your simulation: it hands your step the recorded inputs, tick by tick, checking the recorded hashes as it goes. It can jump to any tick (it restores the nearest saved state before it with load and plays forward from there), run faster or slower, pause and loop.

class InputRecorder#

class InputRecorder

Records a match of a deterministic game as its inputs: the starting state, then what each player pressed on each tick. Because the simulation gives the same result every time (that is what the fixed timestep and @engine/math are for), playing the inputs back through it reproduces the whole match, and a ten-minute match is a few kilobytes. Every checkpointEvery ticks it also keeps a copy of the game state (so a player can jump into the middle) and every hashEvery ticks a hash of it (so a replay that has stopped matching, after an update changed the rules, is caught at once, not by someone noticing the wrong ending).

Call record(tick, inputs) at the start of every tick, before the simulation runs it, with whatever your simulation takes as input for that tick (anything JSON-able: a map from player to buttons). Ticks must be consecutive.

class ReplayPlayer

Plays a replay back. Give it the bytes (a file, or what ReplayRecorder.finish() returned) and the schema it was recorded with; call update(dt) each frame, and draw history (the same SnapshotHistory a live client draws from, so interpolation code is shared: history.around(player.tickAt)). class ReplayRecorder#

class ReplayRecorder

Records a match as a stream of snapshots, in the same compact delta form the network uses, so five minutes of a world of forty entities is about 1 to 3 megabytes (a full snapshot every keyframeEvery ticks makes it possible to jump to any moment without playing everything before it). Game events (a kill, a chat line, a round start) can be recorded between the frames. It records what the server sent to a viewer (or the full world), so it plays back on any machine, even one whose simulation would not reproduce the match; for a deterministic game that wants tiny files, see InputRecorder.

class SnapshotReceiver

The other end: turns the snapshot packets of a live game (a player's or a spectator's) into snapshots, keeps the ones needed to read the next delta, and says which tick to acknowledge. A delta whose starting point is missing is not an error: it sets needsFull, and acknowledging -1 gets a full snapshot next.

class SpectatorFeed#

class SpectatorFeed

Watching a match: the server keeps the whole world for spectators, a few seconds behind what the players are doing (so nobody can tell a team where the enemy is), and sends it to any number of viewers. All spectators who have the same snapshot as a starting point get the same bytes, so the cost of a hundred spectators is a few encodes, not a hundred.

Each tick, push the full-world snapshot. Each time you send to a spectator, ask for packet(spectatorId, ackTick) (the newest tick that spectator says it has) and send the bytes as they are. The packets have the same layout as a player's snapshot packets (MSG.SNAPSHOT, input ack 0, the delta), so a spectator's client can read them with the normal client code or SnapshotReceiver.
