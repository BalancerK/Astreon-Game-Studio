# Engine plan

Fast-action, 2D, browser multiplayer engine. Zero dependencies in core packages, plain JS + JSDoc, npm workspaces, `node:test`.

## Decisions
- Authoritative server; client predicts only the local entity (sequence-numbered inputs, replay on reconcile); remote entities interpolated ~100 ms in the past.
- Own RFC 6455 WebSocket server/client (no permessage-deflate, `setNoDelay(true)`). Transport behind an interface; WebTransport is an optional adapter package (needs `@fails-components/webtransport`), feature-detected with WebSocket fallback.
- Typed-array ECS; binary protocol with quantization + delta snapshots.
- Rendering: WebGPU primary, automatic fallback WebGL2, then Canvas2D. One shared instance-buffer layout (`Float32Array`), atlas + sorted batches, one draw call per batch. Worker rendering (OffscreenCanvas) WebGL2-only for now.
- Render loop decoupled from sim: fixed tick + `alpha` interpolation, frame time capped at 0.25 s.

## Architectural constraints (from risk analysis)
1. **Transport has reliable and unreliable channels from day one.** WebSocket maps both to one ordered stream; every unreliable message carries a sequence/snapshot ID so the receiver drops stale ones. WebTransport maps unreliable to datagrams.
2. **Rooms share no mutable memory.** A room is a self-contained unit (own ECS, own buffers) addressed only by messages, so it can move to a `worker_threads` worker or process.
3. **Snapshot/ack framework before gameplay.** Client acks snapshot IDs; server keeps a ring of recent per-client baselines; a delta is sent only against an acked baseline, else a full keyframe. Periodic keyframes regardless.
4. **Entity IDs carry a generation counter** so a recycled ID is never mistaken for the old entity.
5. **Determinism rules for shared systems:** only `+ - * /` and `sqrt` (exactly specified); own lookup-table trig; no reliance on `Math.sin/cos/pow`. Reconciliation uses an error tolerance, not bit equality. Cross-browser determinism tests (Chrome, Firefox, Safari).
6. **No per-tick allocation on the server:** pooled buffers, preallocated typed arrays. Drift-correcting tick scheduler on a high-res clock.
7. **Bandwidth budgets:** per-client bytes-per-tick cap with priority culling; spatial-hash interest management (no O(n^2)).
8. **Explicit little-endian `DataView`** everywhere; protocol version in handshake.
9. **Time is driven by server tick numbers**, not wall clock; clock sync uses smoothed RTT samples; tab resume resyncs to the server instead of simulating the backlog.
10. **Security basics:** frame/message size limits, per-IP connection limits, Origin checks, input rate limits, cap on lag-compensation rewind, interest management doubles as anti-wallhack.
11. **Tooling:** `tsc --checkJs` as a dev-only check (no runtime dependency); lint script enforcing package dependency rules (each package may depend only on `core` and `protocol`); network simulator, packet inspector and replay built early.

## Fast movement (ultrafast players and objects)
Design goal: players and projectiles can move many body-lengths per tick without tunnelling, rubber-banding or visible stutter.
1. **Swept collision (CCD):** movement is resolved as a swept shape from old to new position (segment/AABB/circle sweeps, time-of-impact), never a teleport-then-overlap test, so fast objects can't tunnel through thin walls or targets. Velocity is capped per tick only as a safety limit.
2. **Substepping:** the shared movement system can split a tick into N substeps when speed x dt exceeds a fraction of the smallest collider; N is derived from data, not hard-coded.
3. **Broad phase:** a uniform spatial hash over typed arrays (cell lists as index ranges, no per-tick allocation); swept queries walk only the cells along the movement segment (grid traversal).
4. **Higher tick and input rates:** tick rate is per-room config (20-120 Hz). Inputs are sampled at render rate and batched with the last N inputs per packet (redundancy against loss), each stamped with a client tick and a sub-tick offset so the server applies them at the right moment.
5. **Send velocity with position:** snapshots carry quantized position and velocity, so the client can interpolate with a Hermite/cubic curve and extrapolate (dead reckoning) for a short capped window (~1-2 ticks) when a snapshot is late.
6. **Adaptive interpolation delay:** target delay = 2 snapshot intervals + jitter estimate, shrinking on good networks (lower input-to-display latency for fast movement) and growing on bad ones.
7. **Quantization sized to speed:** position resolution and range are per-component schema parameters, with a test that the quantization error stays below the smooth-correction tolerance at maximum speed; positions wrap/clamp to world bounds.
8. **Projectiles:** deterministic projectiles (spawn tick + origin + velocity) are sent once and simulated locally on both sides instead of being streamed every tick; only hits/corrections are networked. Hitscan uses lag-compensated rewind.
9. **Cheap smoothing:** reconciliation corrections blend over a few frames and are skipped below tolerance; teleports/respawns are flagged so interpolation doesn't smear across them.
10. **Hot-path discipline:** movement/collision loops run over monomorphic typed arrays with no closures or object allocation; benchmark target to be set in M1 (entities moved + swept per ms) and tracked in CI.

## Modularity and maintainability
1. **Everything is a plugin.** Engine features (physics, renderer, interpolation, interest management) are `plugin(app)` functions that register components, systems, resources and events on an `App`. Server = App without render plugins; client = App with them. Dropping a plugin must leave the rest working (Bevy model).
2. **Systems declare ordering, not slots.** `app.addSystem(fn, {reads:[...], writes:[...], before:[...], after:[...]})`; one scheduler resolves order and reports cycles with a readable error. No global stage list to edit.
3. **Plugins talk through events and public components/resources only**, never another plugin's private data (avoids hidden coupling Bevy users report). Each plugin exposes a small documented `index.js` surface; internals live in `internal/` and are not importable by other packages.
4. **Boundaries enforced by a ~50-line zero-dependency script** (`tools/check-deps.js`): reads each package's `package.json` + scans imports, checks against an allowlist of permitted edges (default deny), fails `npm test`. Also bans deep imports into another package's `internal/`.
5. **One way to do things:** ECS-only game API (no parallel OOP flavour, to avoid the "two flavours of examples" confusion seen in Excalibur). Small API: `App`, `plugin`, `system`, `component`, `resource`, `event`. Consistent naming (`isX`/`canX` booleans, verbs for systems).
6. **Types:** JSDoc + `tsc --checkJs` as dev-only check (Svelte team precedent). Keep types simple (plain object shapes, typedefs); put complex generics in `.d.ts` only if needed.
7. **Debuggability built in:** deterministic replay = log of (tick, client, input) + RNG seed + periodic state checksum; replay runs as CI regression tests (hash of final state); first checksum mismatch pinpoints desync tick. Headless mode for server/tests; debug overlay and packet inspector are plugins.
8. **Docs as code:** each package has a 1-page README (purpose, public API, what it must never import); `docs/ARCHITECTURE.md` with the dependency graph generated by the check script; examples are tested.
9. **Small files, small functions:** target < 300 lines per file; hot-path code is the only place allowed to trade readability for speed, and must carry a benchmark and a comment saying why.

## Plugins and modding
Goal: third parties can extend the engine safely. Decision: both the core team and the public write plugins/mods, and the engine is open source, so tiers 1, 2 and 3 and the bundle protocol are all in scope (M4b is mandatory, not optional). Public/untrusted code is the default assumption for anything a server loads from outside the first-party set.
1. **Manifest + `definePlugin({...})`.** Declares id, version, engine-version range, dependencies, and the components, events and messages the plugin owns. A resolver orders loading and rejects conflicts and missing dependencies with readable errors.
2. **Namespaced registries.** Components/messages are named `modid:name`. Numeric wire IDs are derived from the name hash or from a table sent in the handshake, so client and server agree even with different mod sets (mismatch = refuse join with a clear reason). Protocol schemas can be registered at runtime.
3. **Three mod tiers:**
   - Tier 1, data-only (JSON: stats, sprites, atlas entries, rules). Always safe, default path; most mods need no code.
   - Tier 2, sandboxed scripts: run in a `worker_threads` worker with a per-tick time budget and kill switch, vetted by the server. (`node:vm` is not a security boundary.) Ties to the isolated-rooms rule.
   - Tier 3, trusted native plugins: full access, for first-party or private servers.
4. **Plugin bundle protocol.** Server advertises (id, version, content hash) in the handshake; client fetches and verifies bundles before joining so prediction runs the same code as the server. Replays record the plugin versions used.
5. **`PluginContext` exposes only deterministic tools:** seeded RNG, trig lookup table, tick time, events. No wall clock. Lint/runtime checks flag `Math.sin/cos/pow`, `Date.now`, `Math.random` in shared systems.
6. **System-set overrides:** engine systems are grouped in named sets (e.g. `movement`); a plugin may `replace` or `disable` a set. Done explicitly and logged loudly; conflicts between two replacers are an error.
7. **Dev hot reload** for tier 2/3 plugins; state migration hook (`migrate(oldVersion, state)`) for versioned plugin data.
8. **Client-side mods are untrusted.** Authoritative decisions stay on the server; client plugins may only affect presentation (render, UI, audio, input mapping) unless the server's bundle list includes them.

## Open source and developer experience
The engine serves many developers building different games, so the engine itself is a product with three audiences: game developers (use the engine), plugin/mod authors (extend it), and contributors (change it).
1. **License and governance:** pick a permissive license early (MIT or Apache-2.0; Apache-2.0 adds a patent grant, decision pending), `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md` (private vulnerability reporting; matters because we ship a network server and a sandbox), `GOVERNANCE.md` (how decisions and releases happen).
2. **API stability:** semantic versioning per package; a documented public API surface (`index.js` only), a deprecation policy (warn for one minor before removal), a changelog, and an engine-version range in every plugin manifest. API-extractor-style check in CI fails on accidental public API changes.
3. **Starter experience:** `npm create`-style scaffolder (zero-dependency script) producing a working client+server game in under a minute; templates (minimal, top-down shooter, io-style arena); a plugin template with manifest and tests.
4. **Docs for each audience:** getting started, guides (networking model explained in plain language, prediction, plugins), per-package READMEs, generated API reference from JSDoc, and runnable, tested examples. Architecture doc stays the contributor entry point.
5. **Mod author tools:** plugin validator CLI (manifest, determinism lint, size/time budget check), local sandbox runner with the same limits the server enforces, test harness that runs a plugin headless under the network simulator.
6. **Tooling for everyone:** debug overlay, packet inspector, replay viewer, network simulator, bot swarm, benchmark suite - all shipped as plugins/CLI so users get them for free.
7. **Security posture for public code:** tier 2 workers get memory limits (`resourceLimits`), per-tick time budget, no filesystem/network access, message-size caps; strike system disables misbehaving mods; plugin bundles are content-hashed and optionally signed. Threat model written in `docs/SECURITY.md` before M4b.
8. **Quality gates in CI:** tests, dependency-rule check, determinism check, type check, benchmark regression, lint for banned APIs in shared systems; runs on Windows, Linux and macOS and Node LTS versions.
9. **Community surface:** issue/PR templates, labelled "good first issue" tasks, plugin registry/index (a simple JSON list in the repo at first), example gallery.

## Packages
- `core`: fixed loop (done), typed-array ECS, event bus, seeded RNG.
- `protocol`: schemas, encoder/decoder, quantization, delta snapshots, inputs.
- `transport`: interface + in-memory, WebSocket (own RFC 6455), WebTransport (optional).
- `server`: tick loop, rooms, input queues, interest management, lag compensation.
- `client`: input recorder, prediction, reconciliation, interpolation, clock sync.
- `input`: actions and bindings over keyboard, mouse, gamepad and touch, contexts, rebinding, saving (done, M8 step 2).
- `audio`: Web Audio mixer (buses, limiter), positional sound, voice limits, music, sounds synthesized in code (done, M8 step 1).
- `render`: `createRenderer` (WebGPU -> WebGL2 -> Canvas2D), camera, atlas, batcher, debug overlay.
- `tools`: network simulator, bot swarm, benchmarks, packet inspector.

- **M2 done** (83 tests + browser checks): own RFC 6455 WebSocket server/client; `render` package (SpriteBatch, Atlas, Camera, Canvas2D/WebGL2/WebGPU renderers with automatic fallback); `examples/arena` playable demo (authoritative server, delta snapshots, interpolation). `npm run test:browser` drives headless Chrome 154: all three renderers pass pixel checks and play the live demo; server tick averages 0.18 ms with 41 entities.
- M2 findings: (1) a quantized axis `q(-1,1,8)` cannot represent exactly 0 and would drift, so inputs use integer axes; (2) in a world where every entity moves every tick the encoder correctly sends full snapshots (21 KB/s per client at 41 entities), so deltas are only exercised in calmer scenes and interest management matters; (3) WebGPU worked in headless Chrome, but that environment is software-rendered, so no WebGPU-vs-WebGL2 performance conclusion can be drawn yet.

Autobahn|Testsuite not yet run (needs Docker); our own parser is covered by RFC-derived unit tests, a randomized fragmentation/chunking property test and fuzzing.

- **M3 in progress (prediction done):** server input queue + client prediction/reconciliation in the arena demo, 95 tests. Measured in headless Chrome with 100 ms simulated lag each way: first visible movement of the local player 21 ms with prediction vs 326 ms without, 0 corrections. Over a deterministic simulated network (virtual clock): 0 corrections on a healthy link, <=6 corrections in 900 ticks at 10% loss + duplication + reordering, and exact convergence even at 40% loss.
- M3 design and findings: inputs are applied strictly in sequence, one tick of movement each, so server and client results depend on the input sequence and never on timing; credit-based pacing (one input per tick, small banked credit) absorbs jitter but caps flood/speed-hack at the tick rate (tested); lost inputs are filled by repeating the previous input; the same `applyInput` (with float32 rounding after every step) runs on both sides; corrections are replayed from the server state and hidden by a decaying visual offset that keeps the rendered position continuous (tested). Bug found by tests: entity id 0 is valid, using 0 as "none" left the first player unsimulated (fixed: -1). `simulateLink` wraps any transport (also used by the demo via `?lag=&jitter=&loss=&predict=0`).
- **M3 adaptive interpolation done** (106 tests): new `packages/client` with `InterpolationClock` (lateness, jitter and peak-gap tracking, bounded-rate slewing, latency-step detection) replacing the fixed 100 ms delay; `ArenaClient` measures input-to-ack RTT. Tuned with a deterministic network lab (`tools/arena-netlab.js`, `arena-netlab-sweep.js`): the first defaults starved 4% of frames at 10 ms jitter, so k=4 and a 2-tick minimum were chosen. Result: on a good link other players are drawn ~10-18 ms behind the newest snapshot instead of ~85 ms with a fixed delay, with ~0% starvation; on jittery/lossy links it buffers more (63-107 ms) and stays smooth. Browser check with 100 ms + 30 ms jitter: RTT ~234 ms, 35 ms behind, prediction still reacts in 21 ms.
- **M3 cross-engine determinism done** (109 tests + browser checks): `tools/determinism.js` runs the shared simulation (movement, swept collision, sliding, quantization, snapshot bytes, prediction replay, interpolation clock) and hashes every result bit-for-bit in Node 24 (V8), Chrome 154 (V8) and Firefox 157 (SpiderMonkey): all 7 suites are identical on all three, and golden hashes are committed so any behaviour change fails `npm test`. A deliberate probe shows engines DO disagree on the Math functions the language leaves unspecified: sin/cos/tan differ across all three, and Node and Chrome (both V8, different versions) differ on 9 of 13 probed functions (atan, exp, log, sinh, cbrt, expm1, log1p, atan2 plus the trig ones), while pow and hypot differ in Firefox only. So the rule "shared code uses only + - * / sqrt" matters even for a Node server with a Chrome client. It is now enforced by `tools/check-shared-math.js` (bans those functions, Math.random, wall-clock time and `**` in shared simulation code; `determinism-ok` comments opt out render-only lines); it caught `Math.hypot` in the physics sweep and prediction code, and `2 ** n` in the protocol, all replaced.
- Firefox 157 also verified: render self-test (Canvas2D and WebGL2 pass the pixel checks; WebGPU API present but no GPU adapter in headless, and `createRenderer` correctly fell back to WebGL2), and the live demo with prediction under 100 ms +- 30 ms lag (local player reacts in 4-19 ms, 0 corrections). Observation: in headless Firefox the Canvas2D backend measured a higher RTT (331-451 ms vs ~235 ms for WebGL2): a software-rendered main thread delays message handling; prediction still responds immediately.

- **M4 interest management + bandwidth budgets done** (`packages/server`, 128 tests): `InterestGrid` (grid over positions, enter/leave radii with hysteresis, generation-safe, nearest-first cap) and `ClientReplicator` (per-client view history so deltas are against what that client was actually sent, priority accumulator by distance, AIMD controller to a bytes/second budget; the player's own entity and newly visible entities are always fresh). Verified by exact reconstruction under ack lag and loss, and measured on the real arena server: with 150 bots a client costs 81 KB/s for the whole world, 20 KB/s at a 700-unit view, 8 KB/s at 400; with 400 bots 202 -> 51 KB/s, and budgets of 30 and 15 KB/s land at 28.9 and 15.8 KB/s; server tick time about halves; 0 prediction corrections throughout. Findings: (1) a budget cannot go below the cost of mandatory updates (each refreshed entity is re-sent in every delta until acked, so the floor is about minUpdates x ack lag x entity size); my first default minUpdates = 8 made a 15 KB/s budget unreachable (27 KB/s) until lowered to 2; (2) without a budget, a world where everything moves every tick still falls back to full snapshots, so deltas pay off only once fewer entities change per tick.
- **M4 lag compensation done** (138 tests + live browser check): hitscan combat in the arena (health, damage, death/respawn, walls block shots, shot events to the shooter and nearby clients). The fire input carries aim and the tick the shooter was looking at (quarter ticks, mod 65536); the server rewinds to it, clamped to a window (default 250 ms), using the per-client **views it actually sent** (`ClientReplicator.positionAt`) instead of a separate world history: this judges exactly what the shooter saw, includes budget-stale entities, and means entities outside the shooter's view cannot be hit. Fire is treated as an event (not repeated when lost inputs are gap-filled). Results at 100 ms each way with the shooter always aiming at the displayed target: deterministic lab 30/30 hits with rewind vs 1/30 without (also 40/40 with 80 ms +- 30 jitter and 8% loss; capping the rewind at 50 ms drops it to 3%, so the cap really bounds it); real browser + real server (Chrome, WebGL2, ~213 ms RTT, two runs): 54/54 shots and 8-10 kills with rewind vs 12-20 of 54 (22-37%) and 1 kill without (the "without" figure varies with where the bots are). Test-writing findings: my harness's target died after 4 hits and respawned off-path (the game was right); a victim that respawns out of view is correctly absent from the shooter's snapshot. Schema change: replicated `Health`, input now carries aim and view (determinism golden for snapshotBytes regenerated and re-verified identical on Node/Chrome/Firefox).
- **M4 rooms done** (`RoomManager`, `WorkerRoom`, `InlineRoom` in `packages/server`; arena gateway at `/ws/<room>`, `/rooms`): each room is a self-contained simulation behind the normal Transport contract, in its own worker thread or inline. Sockets stay in the gateway and are proxied as transferable buffers. Measured: a room blocking for 700 ms leaves another room with a 31 ms worst tick gap in worker mode versus 701 ms inline; a crashed room disconnects only its own players and restarts on demand; limits (rooms, players per room, room names), idle cleanup and prompt shutdown are tested. Scaling finding: workers did not make rooms faster (inline also sustained 8 rooms of 1,500 bots and 8 players at about 2 ms/tick; my benchmark shares one process between clients and gateway, so it saturates before workers matter), so the benefit is containment and multi-core headroom. Bug found: `Buffer#slice` is a view, not a copy, which broke cross-thread transfer. WebSocket route functions added (`path` can be a function exposing `connection.route`).
- **M4 reconnect/session resume done** (live browser check plus tests): WELCOME carries an unguessable session token; a dropped player stays in the world, frozen, for a tick-counted window (15 s); the client reconnects with exponential backoff and gets the same entity, position and health back (also over a real WebSocket into a worker room, and in Chrome after killing the live socket: same entity id, 3.9 units from where it was, 0 prediction corrections). Takeover of half-open connections, forged or unknown tokens, expiry, backoff and give-up, deliberate close and rejection are tested. **A flaky test exposed a real bug in `PredictedPlayer`**: a snapshot acknowledging inputs sent before prediction started made the next snapshot snap to the server state without replaying the pending input (one step of error, extra corrections). Fixed (adopt the server state at the ack and replay when the later inputs are remembered; fill in the missing baseline; only count visible changes) with a regression test; the flaky test went from about 1-in-5 failures to 10/10 passes.
- **M4b modding done** (`packages/mods`, `docs/MODDING.md`, `docs/SECURITY.md`; 204 unit tests, plus a live browser check in `tools/arena-mods-test.js`). Tier 1 (data) and tier 2 (script) mods with the bundle protocol:
  - **Sandbox** (4 layers, all measured, see SECURITY.md): hardened `node:vm` context (strings-only boundary, frozen intrinsics, no code generation) inside a **separate child process per mod** with `--permission` (no files, spawn or workers; probe from inside confirmed), heap cap, below-normal priority, per-call CPU budget plus a host watchdog. Findings: the permission model does not block network (documented residual risk: run in a container); a memory bomb dies in about 110 ms and only takes its own process; interrupting promise jobs inside `node:test` crashes Node (async hooks), so those cases run in a clean subprocess; Windows re-adds its standard environment variables after `env: {}`.
  - **Manager**: policy (script on/off, signature required for scripts or all, trusted Ed25519 keys, bundle-hash allow list, mod count, limit caps), dependency order through the core resolver (an unsatisfiable mod is rejected alone), non-blocking per-mod frames (a busy mod is skipped, never queued), strikes with expiry, bounded restarts, validated typed commands (the game re-checks every target against live state), rule merging with conflict report, hot reload with `serialize` state handover.
  - **Bundle protocol**: WELCOME advertises `{id, version, sha256}`; the client downloads `/mods/<id>/<hash>` (immutable, content-addressed), verifies, and refuses to play (no auto-reconnect) on mismatch or failed download. Data mods change shared rules on both sides, so prediction stays exact: 0 corrections over 184 reconciles in Chrome against a modded server; a client that ignores the mod is corrected constantly (control test).
  - **Arena**: instance-based rules with a range-checked whitelist (`RULE_SPEC`), presentation whitelist (colours, title), ops heal/damage/teleport/message (mods cannot kill; teleport refused inside walls), sample mods (fast-weapons, neon-theme, healing-aura, kill-feed) and a template, `tools/mod.js` (validate, run, keygen, sign, pack, selftest). Works through the gateway into worker rooms.
  - **Verified abuse cases**: spinner, memory bomb, command flood, invalid commands, oversize results, exceptions, constructor-chain escape attempts, tampered/unsigned/unpinned bundles, route traversal; honest mods and the tick (max 1.4 to 15 ms bound) unaffected.
  - Test-hardening lesson: timing-based assertions flaked under parallel test files (2 ms vm budgets, 50 ms load budget, fixed number of event-loop turns for async crypto). Fixed by generous budgets in non-timing tests, a 250 ms load budget, waiting on state instead of turns, and unref'd child processes (a failed test used to hang the whole run because an unstopped sandbox kept Node alive).

- **Polish: sprite sorting and text done** (`packages/render`; 16 render unit tests plus pixel checks on Canvas2D, WebGL2 and WebGPU in headless Chrome). **Sorting:** `push(..., tint, key)` and `sortKey(layer, y)`; the key lives in a parallel array (the 40-byte instance layout and shaders are unchanged); a stable LSD radix sort on the float32 key bits, run by every renderer, free when keys arrive in order (3 ms for 50,000 sprites). **Text:** `Font` rasterises glyphs lazily into the existing atlas with the browser's text engine (so any font, accents, CJK and emoji work), draws them as ordinary tinted sprites (no new shader, no extra draw call), with alignment, word wrap, shadow, device-pixel snapping and graceful degradation when the atlas fills. **Overlay passes:** `render({ clear: null })` keeps the previous contents and `Camera.screen(w, h)` gives pixel coordinates, so HUD text is crisp whatever the world zoom is. The arena now draws HP numbers over wounded players and mod messages through the engine. Not done: SDF text, kerning/shaping, multiple atlases.
- **Polish: process-per-room done** (`ProcessRoom` in `packages/server`, `--mode process` in the arena; 228 tests). The worker host was refactored into a shared `ChannelRoom` base plus a transport-independent `startRoomRuntime`, so worker and process rooms share all proxying, start-timeout, crash and shutdown logic, and the existing room tests pass unchanged. Process rooms add: per-room heap cap (`memoryMb`), scrubbed env, optional permission-model confinement (`confine`), pid/memory reporting, exit when the gateway dies, kill after a stop grace period. Measured: a memory bomb dies in about 150 ms and only takes its own process; a room hung for 2.5 s leaves siblings' round trips under 100 ms; 8 rooms average 0.46 ms/tick (worker 0.36, inline 0.18); the isolation numbers match worker mode (other room's worst gap 32 ms vs 701 ms inline). Findings: (1) with `--permission` the room must also read the sibling engine packages it imports, so the host allows the `packages` directory automatically; (2) arena rooms with script mods need `--allow-child-process` for the mod sandboxes, which weakens the room's own confinement (Node prints a SecurityWarning); (3) an `unref`'d child with nothing else alive made `await room.ready` and `await stop()` end the program silently ("unsettled top-level await"), so the host now keeps the program alive while starting and stopping; (4) `stdout` written right before a hard `SIGKILL` is lost on Windows, so the orphan test passes the pid through a file. Not done: restarting a crashed room automatically while keeping its players (they reconnect and get a fresh room), CPU limits and affinity, a per-room network namespace.
- **Polish: predicting your own shots done** (`examples/arena`; 65 arena tests plus a live Chrome check). The tracer and hit burst now appear the instant you fire. Design: `traceShot`/`rayCircle` moved to `shared/shot.js` so server and client run the same code; the client traces from its predicted position along the same quantized aim against the world it displays at the view tick it reports (what lag compensation rewinds to). **Cooldown is now counted in the player's own applied inputs** rather than server ticks, which lets the client predict exactly when a shot is accepted (predicted shot count equalled accepted shots for cooldowns 5, 10, 23; 100% of 47 live shots agreed); abuse is still bounded because inputs apply at most one per tick over time (flood and sequence-jump test). - **Polish: WebGPU vs WebGL2 benchmark done** (`tools/render-bench.js`, `npm run bench:render`, results and analysis in `docs/BENCHMARKS.md`). Real GPU (RTX 5060 laptop; headless Chrome 154 does use it, contrary to the earlier assumption that headless means software rendering), 3 runs with alternating backend order, pipelined throughput and CPU time measured separately because a WebGPU `onSubmittedWorkDone` wait costs about 3 ms by itself (my first, synchronised numbers made WebGPU look 15x slower at small counts: a measurement artefact). Findings: parity for realistic loads (both under 0.3 ms at 10k sprites, 144 fps at 50k); WebGPU ahead at 50k but unstable at 100k between sessions, WebGL2 1.3x faster at 200k (cliff not investigated). **The benchmark was repeated on a clean machine after I found a stray runaway process of mine had been running during the first session; qualitative conclusions held, the 100k ordering did not**; WebGL2 uses less main-thread time and starts 3.5x faster; overdraw-bound scenes identical; Canvas2D pathological with many distinct tints. **Conclusion: no performance case for either backend on this hardware; the default order stays a product decision (reach and future features), to be revisited with integrated-GPU and Android numbers.** Not done: integrated GPU, other vendors, mobile (Android is deliberately last).
- **Polish: multi-page atlas and SDF text done** (`packages/render`; 23 render unit tests; 25 pixel checks per backend in headless Chrome). **Atlas pages:** the atlas grows by itself (new page when full, up to `maxPages`), all pages are layers of one texture array (WebGL2 `TEXTURE_2D_ARRAY`, WebGPU `texture_2d_array`), per-page versions so only changed pages upload, the array grows when pages are added after the first frame (tested), and one draw call still draws everything. The instance layout went from 10 to 11 words (meta word: page in bits 0-7, SDF flag at bit 8). **SDF text:** `Font({ sdf: true })` stores glyphs as distance fields (exact Euclidean distance transform, verified against a brute-force reference; 128 = outline) and the shaders threshold them with a screen-space-derivative width: 0 soft edge pixels at 10x the stored size on WebGL2 and WebGPU versus 16 for scaled raster text; Canvas2D falls back to a coverage conversion (8 soft pixels, still sharper than scaled raster). Findings: (1) `meta` is a reserved word in WGSL, and the resulting shader error is silent (an empty frame), so WebGPURenderer now logs shader compile errors and uncaptured validation errors and keeps `lastError`; (2) my first Canvas2D SDF path drew whole glyph cells (it copied the mask after filling the colour), caught by the stem-width check; (3) derivatives (`fwidth`) must be computed outside the SDF branch for uniform control flow; (4) default atlas `maxPages` is 8 (a 1024 page is 4 MB, so 32 MB at most). Not done: SDF outline/glow (needs a second colour in the instance), kerning, user textures beyond atlas pages.

## Research findings (round 3)
- `setNoDelay(true)`: Nagle is ON by default in Node sockets (never changed); call it on every accepted game socket. Estimated up to ~40 ms added otherwise.
- Tick rates in the wild: Apex 20, CS2 64 + sub-tick (inputs timestamped, processed between ticks), Valorant 128 (anecdotally ~60-128 under load), Marathon 60. Sub-tick input timestamps are worth copying; default tick 60 Hz, configurable up to 120.
- Interpolation: Hermite spline using per-sample velocity (Gaffer on Games) lets us keep a low snapshot rate; Unity caps extrapolation (20 ticks default) - ours caps at 1-2 ticks.
- PixiJS v8 says WebGPU is not automatically faster; its win is scenes with many batch breaks (filters, masks, blend modes), and CPU is often the bottleneck for plain sprites. So: WebGL2 and WebGPU must be benchmarked head-to-head with our own batcher before WebGPU is made the default.
- WebTransport: datagrams for state + reliable stream for control is the recommended pattern; QUIC/UDP is blocked on some corporate networks, so WebSocket fallback is mandatory. Node server side remains the weak point.
- Autobahn|Testsuite (500+ cases, Docker, fuzzingclient mode) is the conformance gate for our WebSocket server; it does not cover backpressure, so we add our own slow-client tests (`write()` return value / `drain`).
- Swept collision: Unity documents sweep-based TOI CCD vs cheaper speculative CCD (expanded broad-phase AABB; can give ghost contacts). We use sweep TOI. Grid traversal (Amanatides-Woo DDA) is not covered by sources found; implement from the paper and test.
- Not found / unreliable: Node QUIC status, WASM SIMD + SharedArrayBuffer ECS for game servers (only generic material; one blog's Node 26 claims look unreliable).
